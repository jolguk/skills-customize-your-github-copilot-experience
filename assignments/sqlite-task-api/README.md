# 📘 Assignment: Persistent Task APIs with SQLite

## 🎯 Objective

Extend your FastAPI task tracker with SQLite so tasks survive application restarts. Practice parameterized SQL, database constraints, transaction handling, and isolated persistence tests in this advanced assignment designed for two or three class periods.

## 📝 Tasks

### 🛠️	Create Persistent Task Storage

#### Description
Start from your completed Building REST APIs with FastAPI assignment. Use Python's built-in `sqlite3` module to replace in-memory storage with a local database file. Plan to complete database setup in the first period, CRUD integration in the second, and testing in the third; combine setup and integration for a two-period schedule.

#### Requirements
Completed program should:

- Create a `tasks.db` file and a `tasks` table automatically when the application starts for the first time.
- Use an integer primary key generated by SQLite, a required text title, and an integer completion flag that defaults to `0`.
- Enforce title length between 1 and 100 characters after trimming surrounding whitespace, and constrain completion values to `0` or `1` at the database level.
- Initialize the schema with `CREATE TABLE IF NOT EXISTS` so restarting the application does not erase existing data.
- Allow a different database file path to be supplied for tests without modifying the production database.
- Keep database access separate from route handlers, close connections after use, and avoid sharing one global connection across requests.

### 🛠️	Connect CRUD Routes to SQLite

#### Description
Update your existing task endpoints to read and write database records. Preserve the API's JSON contract while converting SQLite's integer completion values to JSON booleans.

#### Requirements
Completed program should:

- Use SQL placeholders for all user-supplied values; never build SQL by concatenating or formatting input into a query.
- Implement `POST /tasks` to insert a task, use its database-generated ID, and return the created task with status `201`.
- Implement `GET /tasks` to return all stored tasks ordered by ID, or an empty array when no tasks exist, with status `200`.
- Implement `GET /tasks/{task_id}` to retrieve one stored task with status `200`.
- Implement `PUT /tasks/{task_id}` to replace the required `title` and `completed` fields while preserving the ID, returning the updated task with status `200`.
- Implement `DELETE /tasks/{task_id}` to remove the stored task and return status `204` with no response body.
- Return task objects with integer `id`, string `title`, and boolean `completed` fields, and preserve the existing `GET /` health endpoint.

For example, creating a task might return:

```json
{"id": 1, "title": "Practice SQL queries", "completed": false}
```

After stopping and restarting the server with the same database file, requesting that task should return the same data.

### 🛠️	Protect Data Integrity

#### Description
Keep request validation in Pydantic and use database constraints as an additional safeguard. Make transaction boundaries explicit so successful changes persist and failed writes leave no partial changes.

#### Requirements
Completed program should:

- Trim surrounding whitespace from titles before storing them and reject empty or overlong normalized titles with status `422`.
- Return status `422` for missing required request fields or a non-integer task ID in the URL.
- Return status `404` with a JSON `detail` message when reading, replacing, or deleting a task that does not exist.
- Commit successful writes and roll back failed transactions; do not report a write as successful before its transaction commits.
- Leave existing records unchanged after rejected requests, missing-task operations, or failed transactions.
- Store titles containing apostrophes or SQL-like text as ordinary data without changing the schema or unrelated records.

### 🛠️	Verify Persistence and Isolation

#### Description
Use `pytest`, FastAPI's `TestClient`, and temporary database files to test the API and database layer. Install testing dependencies with `python -m pip install pytest httpx` and run the suite with `python -m pytest`. Use a fresh temporary file for each test rather than the development database.

#### Requirements
Completed program should:

- Pass an end-to-end test that creates, lists, reads, replaces, and deletes a task, checking status codes and JSON data.
- Prove persistence by creating a task, closing the first application client and its connections, then creating a fresh application instance using the same temporary database file and retrieving that task.
- Confirm schema initialization preserves existing records when repeated.
- Verify `404` responses for missing tasks and `422` responses for invalid titles, missing required fields, and non-integer path IDs.
- Verify that a title containing an apostrophe and a title containing SQL-like text are stored literally and leave the table and other records intact.
- Test database constraints directly by attempting invalid title and completion values, then checking that invalid rows were not saved.
- Prove rollback by inserting a valid row and then triggering a constraint failure in the same transaction; after rollback, verify that neither write persisted.
- Run tests independently and in any order without changing the development database.
